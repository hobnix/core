# Recipes, packages, extensions

Loaded when you touch the files above (path-scoped rule). The root CLAUDE.md has the rules that always apply.

- **One default repository (since the switch of #1074):** config/package-repos.toml has only the row `official` (signed index https://hobnix.github.io/official/index.json, `replaces = [recipes, extensions]`, `core = [...]` the names the core refers to: read by scripts/dev/core-names-check.py in CI only; `hs pkg install --core` installs what the index flags `core = true`; `repo add` refuses a name listed in `replaces`). The old rows are gone as defaults; `hs pkg repo migrate` (run by `hs update` and every fetch) moves installed packages recorded under them, never downgrades, never touches an added repository. The three old repositories are archived, not deleted; their allowed_signers files stay one release. The next bullet is the history before the switch.
- **Where the packages live (since 2026-10-29):** the recipes are in github.com/hobnix/recipes (`recipes/<name>/`) and the extensions in github.com/hobnix/extensions (`extensions/<name>/`), not in this tree. A package is changed there (sibling checkouts, e.g. ../hobnix-recipes), released with a signed tag `vX.Y.Z` (key: config/trusted-keys/), and reaches a server with `hs pkg install|update`; `hs pkg install --core` (called by `hs first-run`) fetches the packages the core refers to by name. Their tests run in their own repositories against a checkout of this one (`HS_CORE=<this tree> bash tests/run-all.sh`). This tree keeps the loaders, the shared helpers (scripts/recipes/_lib.sh, _media.sh, files/) and a small fixture package tree for its own tests (tests/fixtures/pkgtree). Where the text below says `packages/<name>/` or `capabilities/games`, read: the package repository.

- **Package surface, trust rules** (hobnix/core#1072, docs/Package-API.md "What the core refuses", all fail closed): no package row shadows a core row (install and update refuse the whole package: scripts/lib/pkg-stage-check.sh).
  No first word or option key that the core or another package has (schema-gen.py overlay, registry-load.sh).
  No public route to an admin page (`[app.routes]`, pkg_app.py).
  A package `[[probe]]` must name a `reads` row of its own package, or a `changes` row ending in `--dry-run` that passes it on (`probe_is_read` in scripts/smoke.sh, tests/smoke.sh). It catches package mistakes, not hostile packages (flags and script are the package's).
  A `start` sys row needs its `plan` row; the typed name stays a review rule. Dependents: scripts/lib/pkg-deps.sh.

- **Releasing a package repository:** inside the checkout of hobnix/recipes or hobnix/extensions, `bash <core>/scripts/dev/release.sh [patch|minor|major]` (on main, clean, equal to origin/main) signs the next `vX.Y.Z` (`--version vX.Y.Z` for the first; `--dry-run` only checks) with `~/.ssh/hobnix_release.pub`, verifies it against config/trusted-keys and pushes it; `release.sh bump <package> [patch|minor|major] [--pr]` raises one package's version in package.toml and index.toml on a feature branch. `scripts/dev/prepare-release.sh` raises versions from `bump:` labels (no version edit by hand; hobnix/core#615), the reusable workflows `package-prepare-release.yml` and `package-release.yml` run both from GitHub, `scripts/dev/caps-ref.sh` picks the ref of the capabilities repository for CI (default hobnix/official, `main` for a release; ci.yml still passes HS_CAPS_URL of hobnix/capabilities until #1074 C3); a repository with `publish = "index"` in index.toml (hobnix/official) has no tags: release.sh refuses to tag there, prepare-release.sh compares with origin/main, `pkg.py repo-check` demands the kind of the top-level folder (recipes/ recipe ...) and the licences (AGPL root, MIT recipes/); `scripts/dev/merge-package-repos.sh` builds official locally from the three develop histories (never pushes; tests/merge-package-repos.sh); docs/RELEASE-PROCESS.md "Package repositories" has the first-tag checklist. Tests: tests/release.sh, prepare-release.sh, caps-ref.sh.

- **Packages** (docs/PLAN-packages.md; step 1 built 2026-10-28): recipes and extensions are both *packages* with a semver `version` and `requires_core` (the API level in scripts/lib/api-level) in a `package.toml`: `packages/<recipe>/package.toml` (`run.sh` beside it; the header lines of run.sh must agree, tests/pkg.sh) and `capabilities/<ext>/package.toml`. `hs pkg list|updates|validate`, `hs sys pkg list`, scripts/pkg.py; `hs recipe` records the applied version in /var/lib/hs/packages/installed.toml. A new recipe needs its package.toml (`python3 scripts/pkg.py convert scripts/recipes/<name>.sh`). Recipes install themselves from pinned releases (NO community-scripts any more); `piece`/`fetch_pinned`/`ensure_file` in recipes/_lib.sh and `hs recipe <name> --check` do only what changed. A recipe package may carry commands.tsv + `[web.*]` (pilot `arr`: `hs ext arr status`). Repositories: `hs pkg repo|fetch|available|install|update|remove` (scripts/pkg_repo.py; release tags `vX.Y.Z` signed with an SSH key, only the newest tag that verifies against config/trusted-keys/<repo>.allowed_signers (defaults) or the key given at `hs pkg repo add` is used, installs are read-only copies in /var/lib/hs/packages/current, `update` shows the git diff first and needs `--yes` without a terminal; never a branch, never an unsigned tag unless the repo was added `--unsigned`). Step 5 (2026-10-28): recipes moved to packages/<name>/run.sh, the games/posters scripts into their capabilities/ folders (HS_SCRIPTS points them at the core helpers); `python3 scripts/dev/export-package-repos.py [--out <dir>]` writes the clean repositories recipes and extensions (index.toml, one commit, CI that validates against the core via `pkg.py repo-check`); tests/pkg-export.sh proves the way back (signed tag, add, fetch, install). The packages are still ALSO in this repository: they leave it only after the two repositories are published, signed and their keys are in config/trusted-keys/, otherwise a fresh install would have no recipes (the six the core refers to by name are flagged `core = true` in the index). Next: step 6, the public-release cleanup. `hs pkg new <name> --template recipe|extension [--dir <path>]` (scripts/pkg_new.py, tests/pkg-new.sh) writes a package that passes validate/repo-check into a package repository checkout plus its index.toml entry; never overwrites. `--protocol shell|python` (extension only) writes a command that speaks the protocol (`protocol = [1]`, helpers scripts/lib/ext_sdk.sh and ext_sdk.py, examples in sdk/examples incl. Go, guide docs/extensions-sdk.md, tests/ext-sdk-examples.sh).

- **Recipes and apps** (details: docs/Entwicklungsnotizen.md#recipes-and-apps). `hs recipe <name>` runs packages/<name>/run.sh (found by scripts/lib/recipe-path.sh: the checkout, /etc/nixos, or /var/lib/hs/packages/current for one installed from a repository), idempotent, built from the helpers in scripts/recipes/_lib.sh (+ _media.sh; recipes find them through HS_RECIPE_LIB / HS_SCRIPTS, which recipe.sh exports). A file only one recipe uses sits beside its run.sh (`$(dirname "$0")/x`); shared ones stay in scripts/recipes/files (`ensure_container`, `fixed_address`, `step`, `spin`, `in_ct`, `wait_page` (waits for the container's web page, options in _lib.sh), `ok`/`note`/`warn`/`fail`, `box`); never print raw command output, write new ones the same way. `hs recipe <name> --name <container>` (= `RECIPE_NAME`) runs a recipe a second time under a container name of its own; its answers and its service descriptor (named after the container) are separate. Every recipe has the header lines `# kind: generic|personal`, `# needs: docker share tailscale|-` and `# uses: gpu|-` (tests/recipes-meta.sh checks them against the script). A recipe that needs answers up front also has `# input: form` and one `# ask: KEY|label|text|secret|choice:a,b|default|pattern|when` line per question (`hs sys recipes asks`; the web form sends text as `--set KEY=value` and ONE secret on stdin, which the job reads with `answer KEY` from a root-only file; never read a secret from the environment or argv); `# input: terminal` = needs a person at a terminal (domain). Preferences are asked once and stored in /var/lib/hs/recipe-<ct>.conf; the closing text holds only clicks that cannot wait and ends with `$(docs_hint <guide slug>)`. Under `set -euo pipefail` a `$(sed ... missing-file | tail)` kills the script: add `|| true`. Rules: never a Zoraxy rule for admin or login-less pages (Tdarr, Sunshine 47990/8083, Grafana, Matrix hook, docs site); `hs remote` shares are never in /bulk, parity or backup and arr/Tdarr never get them; Matrix messages go in addition to ntfy, never instead of it, and rooms stay unencrypted; never put a `raw.lxc` `lxc.cgroup2.devices.allow` line on an unprivileged container. The game-streaming server container (sunshine) is PARKED (exits unless RECIPE_FORCE=1). Documentation: the page Docs of the web interface (capability `docs`, on with `webUi = true` unless `webDocs = false`; notes capabilities/docs/NOTES.md); `hs docs build` (scripts/docs-build.sh) writes the Markdown and index.json it serves, `hs update` runs it; the recipe `docs` is gone (2026-10-23). A new English-only doc must be named PLAN-*.md or added to the case in docs-build.sh, and listed in docs/categories.tsv and docs/README.md (tests/docs.sh); guides use no raw HTML tags (the renderer shows them as text).

- Pelican: run artisan as www-data (root-owned cache files cause 500s).

- Wings behind Zoraxy: add response headers `User-Agent: Pelican Wings/<ver> (id:<token_id>)`
  and `Access-Control-Expose-Headers: User-Agent`, otherwise the node heart stays red.

- Pelican allocations must use IP 0.0.0.0, not 10.10.95.31 (Docker only DNATs the bound IP,
  breaking Tailscale access).

- Posters (extension `posters`, off by default): `hs ext posters generate` (old word `hs generate poster` is a legacy row for one release; guided, capabilities/posters/generate-poster-guided.sh) over the system command `hs sys ext posters generate` (generate-poster.sh, never asks, key<TAB>value lines) over capabilities/posters/poster.py (Pillow, `python3.withPackages` in configuration.nix; Inter fonts from recipes/files/matrix-card/fonts). Eyebrow and title required, colour and seed random (the colour derived from the seed, so a seed is reproducible). capabilities/posters/guide.md, tests/generate-poster.sh; not run on the server yet.

- **Package index** (docs/PLAN-registry.md "Built: the index format", hobnix/core#1069): `hs pkg index build|validate|sign|verify|tree` (scripts/lib/pkg_index.py) builds `index.json` from package.toml and assets/, signs it with an SSH signature (namespace `hobnix-index`, key only as a file), checks serial and schema; reusable workflow `.github/workflows/package-index.yml` (never run yet). The client (hobnix/core#1070, scripts/pkg_repo.py, tests/pkg-index-repo.sh): a repository row with `index` is read from its signed index (signature, serial never lower, tree hash of the pinned commit, yanked refused); rows without it keep the signed tags (docs/PLAN-registry.md "Built: the client"). Test: tests/pkg-index.sh.
